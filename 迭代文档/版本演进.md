## v3.1 · P3b 增量翻译闭环（核心）

- **时间**：2026-09-15
- **目标**：任务从 ready 到翻译完成的**全自动闭环**
- **核心约束**：**Hermes cron 单次 3 分钟硬中断** —— 长翻译任务会被强制掐断
- **架构决策**（三方分工）：
  - `consumer.py`（脚本）：队列扫描/pick/record/进度/merge 请求，纯机械操作
  - cron agent（`ab9ef9653179`）：只做「翻译 chunk + 翻译书名」的 LLM 工作
  - **merge 放 Web 后台线程**（60s watcher）：避开 3 分钟窗口
- **做了什么**：
  - `consumer.py`：`pick` / `finish` / `request-merge` / `status` 子命令
  - pick 自动 record（防 output 已存在未记录 → 死循环）
  - **断点续译**：output 落盘 → 下轮 pick 自动 record_only 续译，绝不重复翻译
  - merge watcher：60s 周期检测 `merge_request.json` → 自动 `merge_and_build`
  - cron 消费者：每 5 分钟（后改 3 分钟）、agent 模式加载 translate-book skill、local 投递
- **坑**：`merge_and_build --cleanup` 会删 `chunk*.md`/`output_chunk*.md`（查看器对照依赖）→ **watcher 禁用 cleanup**
- **验证**：37 块全闭环（3 块真译 + 34 mock）→ merge → 5 格式成品；最坏单块 268s > 3min 窗口 → 断点续译兜底生效

## v5.5 · E 方案（成品下载流量迁移 Cloudflare R2）  `2026-09-19`

- **时间**：2026-09-19（17:41 代码上线 → R2 凭证填入 → 19:12 首轮归档 10/12 → 19:20 慢链路修复 → 补传对账 12/12 → 19:40 timer 启用）
- **目标**：把成品大文件（`book.pdf`/`book.docx`/`book.epub`）的**下载流量从 VPS 搬到 R2**——原前端 `fetch + Blob` 下载会把整个 53MB 的 PDF 读进浏览器内存，且每次下载都吃 VPS 出网流量
- **做了什么**：
  - 新增 `web/r2.py`：boto3 S3 兼容客户端（`signature_version=s3v4` + R2 endpoint），**幂等上传**（远端同尺寸即跳过）、**签发预签名 URL**（`PRESIGN_TTL=900s`，`ResponseContentDisposition=attachment` 保原名）、按书前缀删除对象；**任何失败只记日志返回 None/False，不抛给调用方**（主流程不受影响）
