## v0.0 · 上游单 skill（移植前）

- **时间**：2026-09-14 前
- **形态**：GitHub 仓库 `Andrew-li777/translate-book`，本质是 **Agent Skill**（`SKILL.md` + 11 个 Python 脚本 + 测试 + 海报资产）
- **能力**：整本书 EPUB → 分块 → LLM 翻译 → 5 格式成品（PDF/DOCX/EPUB/HTML/Markdown）
- **运行方式**：人工调用 skill，`delegate_task` 并行翻译（默认 8 并发），一次性跑完
- **局限**：无 Web 界面、无任务队列、无增量续译、依赖人工触发

## v3.1 · P3b 增量翻译闭环（核心）

- **时间**：2026-09-15
- **目标**：任务从 ready 到翻译完成的**全自动闭环**
- **核心约束**：**Hermes cron 单次 3 分钟硬中断** —— 长翻译任务会被强制掐断
- **架构决策**（三方分工）：
  - `consumer.py`（脚本）：队列扫描/pick/record/进度/merge 请求，纯机械操作
  - cron agent（`ab9ef9653179`）：只做「翻译 chunk + 翻译书名」的 LLM 工作
  - **merge 放 Web 后台线程**（60s watcher）：避开 3 分钟窗口
- **做了什么**：
  - `consumer.py`：`pick` / `finish` / `request-merge` / `status` 子命令
  - pick 自动 record（防 output 已存在未记录 → 死循环）
  - **断点续译**：output 落盘 → 下轮 pick 自动 record_only 续译，绝不重复翻译
  - merge watcher：60s 周期检测 `merge_request.json` → 自动 `merge_and_build`
  - cron 消费者：每 5 分钟（后改 3 分钟）、agent 模式加载 translate-book skill、local 投递
- **坑**：`merge_and_build --cleanup` 会删 `chunk*.md`/`output_chunk*.md`（查看器对照依赖）→ **watcher 禁用 cleanup**
- **验证**：37 块全闭环（3 块真译 + 34 mock）→ merge → 5 格式成品；最坏单块 268s > 3min 窗口 → 断点续译兜底生效

## v5.3 · D 方案（脚本直连 API）长期部署

- **时间**：2026-09-17
- **目标**：把 v5.2 提到的 D 方案落地为生产引擎，突破 cron+delegate_task 的速度与内存瓶颈
- **做了什么**：
  - 写 `translate_direct.py`：systemd 守护（translate-direct.service），绕开 cron agent+delegate_task，ThreadPool(3) 直调 amd API
  - 新增 `fix_images.py`：图片引用后处理（模型翻译插图密集块会丢 `![](images/xxx)` → merge image validation 失败卡死，用确定性脚本补回）
  - **关键发现**：`reasoning_effort` 是吞吐杀手——A/B 实测 none=47-65s/块、medium=141-144s、minimal/xhigh=超时。翻译是直译任务不需要推理，D 默认 `reasoning_effort=none`（2.7x 提速、无超时）
  - **互斥协调**：cron prompt 加 systemctl 守卫——D 服务 active 时 cron 待命，D 失效时 cron 自动接管兜底
  - **修复 finish 缺口**：finish 的 all_done 不写 merge_request.json → watcher 不合并，须显式调 `consumer.request_merge` 触发构建
- **实测**（abtest 测试书 37 块）：单块 47-65s、全书 22 分钟（≈110 块/h，vs cron 26 块/h 实测）、内存 10.8M 常驻、质量与 cron 相当、5 格式成品全生成
- **效果**：速度 ~4-6x、内存 -800MB、无 3 分钟窗口限制
- **遗留**：跑一本真实长书验证长期稳定性；图片修复目前是追加到末尾（可优化为按源行号插回原位）
