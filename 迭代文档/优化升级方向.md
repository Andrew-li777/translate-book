# 优化升级方向

已实现的优化（截至 2026-09-16）与待评估方向。主要矛盾：**翻译速度**与**内存/并发约束**。

## 一、翻译速度优化（核心）

### 现状基线
- cron 3min × 3 块 = **60 块/h** → 200 块 ≈ **3.3h**
- 瓶颈：Hermes cron 3 分钟硬中断 + `delegation.max_concurrent_children=3` + 3.8GB 内存

### 方案对比

| 方案 | 配置 | 吞吐 | 200 块耗时 | 风险 | 状态 |
|---|---|---|---|---|---|
| A 现状 | 3min × 3 块 | 60 块/h | 3.3h | 无 | ✅ 已上线 |
| B 每轮 6 块 | 5min × 6 块 | 72 块/h 理论 | 2.8h | **高**：并发上限 3 + 6 子代理 OOM | ❌ 不可行 |
| C 脚本直连 API | 后台脚本 3-4 并发 | 120–400 块/h | **30min–1.5h** | 中：prompt 复制度需 A/B 验证 | 📋 待评估 |

### D 方案（脚本直连 API）详细设计

**原理**：绕开 cron agent + delegate_task，写 `translate_direct.py` 后台长跑：
```
循环：pick 3 块 → ThreadPool(3) 直调 ark API（prompt=skill 模板+术语表）
     → 写 output → record → 全书完成 → request-merge → watcher merge
```

**复用**（零改动）：consumer.py 队列逻辑、run_state/glossary 接口、merge watcher、progress.json（SSE 无缝可见）
**新增**（~200 行）：API 客户端（重试退避）、prompt 模板、主循环 + direct.log

**关键点**：
1. 密钥复用 Hermes config 的 volcengine-plan provider，不硬编码
2. **质量一致性是最大风险** → 10 块 A/B 对比测试（cron 译文 vs 脚本译文）
3. 内存 ~100-200MB（远低于 agent 方案 ~1GB），3 并发安全
4. D 运行期间暂停 cron（防双写）；D 停用后 cron 兜底

**实施 4 步**：
1. 写 `translate_direct.py` → 2. 密钥连通冒烟 → 3. 10 块 A/B 质量对比 → 4. 通过后暂停 cron、跑全书、验收

## 二、内存优化

- scan 已治理（bge-m3 RAG 关闭、faster-whisper finally 释放）
- translate 侧：agent 方案子代理峰值 ~1GB；脚本方案 ~100-200MB
- 方向：D 方案本身就是最大的内存优化（省 ~800MB）

## 四、建议优先级

1. **D 方案**（速度 2-10x + 内存 -800MB）——价值最高，风险可控
2. 对照阅读细化（同步滚动已做，可加锚点/字数统计）
3. 上传文件名清洗（超长/特殊字符，当前靠 ext4 上限兜底）
