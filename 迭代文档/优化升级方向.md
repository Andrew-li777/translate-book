# 优化升级方向

已实现的优化（截至 2026-09-16）与待评估方向。主要矛盾：**翻译速度**与**内存/并发约束**。

## 一、翻译速度优化（核心）

### 现状基线
- cron 3min × 3 块 = **60 块/h** → 200 块 ≈ **3.3h**
- 瓶颈：Hermes cron 3 分钟硬中断 + `delegation.max_concurrent_children=3` + 3.8GB 内存

### 方案对比

| 方案 | 配置 | 吞吐 | 200 块耗时 | 风险 | 状态 |
|---|---|---|---|---|---|
| A 现状(cron) | 3min × 3 块 | **26 块/h 实测** | **7h45m 实测**(200块) | 无 | ✅ 已上线 |
| B 每轮 6 块 | 5min × 6 块 | 72 块/h 理论 | 2.8h | **高**：并发上限 3 + 6 子代理 OOM | ❌ 不可行 |
| C 脚本直连 API | 后台脚本 3-4 并发 | 120–400 块/h | **30min–1.5h** | 中：prompt 复制度需 A/B 验证 | ❌ 已被 D 取代 |
| **D 脚本直连(amd)已实施** | systemd 守护 3 并发 | **~110-170 块/h 实测** | **~2h** | **已 A/B 验证通过** | ✅ **2026-09-17 上线** |

### D 方案（脚本直连 API）—— 已实施 ✅

**原理**：绕开 cron agent + delegate_task，写 `translate_direct.py` 由 systemd（translate-direct.service）常驻守护：
```
循环(pick 3 块) → ThreadPool(3) 直调 amd API(prompt=skill 模板+术语表)
   → 写 output → fix_images(补缺失图片引用) → finish → 全书完成 → request-merge → watcher merge
```

**实测结果（2026-09-17，abtest 测试书 37 块）**：
| 指标 | 实测值 |
|---|---|
| 单块耗时 | **47-65s**（reasoning_effort=none）|
| 全书 37 块 | **22 分钟**（~1.7 块/min，≈110 块/h）|
| 内存 | **10.8M 常驻**（systemd MemoryMax=1G）|
| 质量 | 与 cron 版本相当（A/B 对比通过）|
| 成品 | HTML/DOCX/EPUB/PDF 5 格式全生成 |

**关键发现：reasoning_effort 是吞吐杀手**（A/B 测试意外暴露）：
| effort | 单块耗时 | 结果 |
|---|---|---|
| none | 47-65s | ✅ 快且稳 |
| minimal | 180s | ❌ 超时 |
| medium | 141-144s | ⚠️ 慢（1536 reason tokens 白烧）|
| xhigh | >180s | ❌ 超时 |
→ 翻译是直译任务不需要推理，**D 默认 reasoning_effort=none**（2.7x 提速、无超时）

**复用**：consumer.py 队列逻辑、run_state/glossary 接口、merge watcher、progress.json（SSE 无缝可见）
**新增**：`translate_direct.py`（API 客户端+主循环+direct.log）、`fix_images.py`（图片引用修复后处理）

**互斥协调**：D 服务 active 时 cron 只待命（cron prompt 加 systemctl 守卫）；D 失效时 cron 自动接管兜底

**Pitfalls（实测踩坑）**：
1. **finish 的 all_done 不写 merge_request.json** → watcher 不合并。须在 finish 后显式调 `consumer.request_merge(job_id, title)` 才能触发构建。
2. **直连 API 会丢图片引用**：插图密集 chunk（如 chunk0003）模型把整块 `![](images/xxx)` 全丢 → merge image validation 失败卡死。须跑 `fix_images.py` 后处理补回。
3. **默认 provider 已切 amd-radeon**（DeepSeek-V4-Flash），key 从 `AMD_RADEON_API_KEY` 读（不硬编码）。

## 五、网络带宽（2026-09-19 实测，重要）

评估 E 方案疗效时顺带测出的**真实瓶颈**（脚本：`/root/scripts/net_speed_probe2.sh`、`egress_probe.py`）：

| 方向 | 实测 | 含义 |
|---|---|---|
| VPS 出网（上行） | **~110 KB/s（≈1 Mbps）** | **本项目真正的瓶颈**：R2 全量归档 207MB 要 ~33 分钟；**任何对象存储/图床/同步上传都必须单分片串行**（问题 #31）|
| VPS 入网（下行） | 5.5–8 Mbps | 上传图书、拉取 chunk 够用（与上行**不对称 6–8 倍**）|
| 经 Cloudflare 下载本站成品 | ~109 KB/s（`cf-cache-status: DYNAMIC`）| 53MB PDF ≈ 8 分钟；CF 不回源缓存（内容需鉴权），下行被**回源上行**拖住 |
| R2 预签名直下 | 与 CF 同量级，但**只吃 R2↔浏览器，不占 VPS 出网** | E 方案的收益实际在这里 |

**结论**：手册给 E 方案的理由（省服务器内存 / 省流量）**在本机并不成立**——实测限速拉 53MB 时 translate-web RSS 仅 **65 → 69MB**；开机 5.4 天 TX 累计 6.14GB、14 天下载 47 次，流量远未触顶。**但 E 方案歪打正着**：它精准绕开了 1Mbps 上行这个真瓶颈。

**替代方案 B（升火山引擎出网带宽）—— 已评估、不采用**：比 R2 更直接地解决根因（0 代码改动），但**用户 2026-09-19 决定不升级带宽**（成本考虑）；分发继续由 R2 承担，本项关闭、不再评估。若日后上行成为硬约束再重启讨论。

## 八、S5 / S6 评估（2026-09-19，实测取证）

### S5「上传走 R2 直传」—— 结论：**原方案前提不成立，按原方案关闭**

**前提证伪（本机实测 2026-09-19，`/root/scripts/probe_inout_speed.sh`，CF speedtest 端点各测 2 次）**：

| 方向 | 实测 | 这条路上跑什么 |
|---|---|---|
| **入网**（服务器接收）| **881.5 / 245.6 KB/s（2.0–7.2 Mbps）** | 用户上传书、服务器从 R2 拉文件 |
| **出网**（服务器发送）| **115.1 / 112.4 KB/s（~0.93 Mbps）** | 推 R2、向用户分发 |

- 那个 1Mbps 是**出网**带宽；而**上传书走的是入网**（2–7 Mbps）。「上传受 1Mbps 上行限制」的原始理由**不成立**。
- 更关键：文件最终**必须落在服务器本地**——Calibre / Pandoc / PDF 导出（Qt WebEngine）全是本地进程。所以「直传 R2」之后仍要 R2→服务器**再拉一次**。
- 字节账：现路径 = 用户 →(CF)→ 服务器（穿越 1 次）；直传方案 = 用户 → R2 **＋** R2 → 服务器（同样字节量，还多存一份中间态、多一条要清理的链路）。**没有任何一条受限链路被绕开**。
- 真正的上传速度上限是**用户自己的上行**（服务器入网 2–7Mbps 不是瓶颈），直传 R2 也救不了这一点。

**但评估中发现 4 个真实存在的上传痛点（与原方案无关）**：

| # | 问题 | 现状证据 | 影响 |
|---|---|---|---|
| 1 | CF 免费版代理请求体上限 **100MB**，与本项目 `MAX_UPLOAD_BYTES = 100MB` **正好撞线** | `web/jobs.py:22`；CF 口径 100MB/Free·Pro（多处来源一致，2026-09-19 核对；**未在本机实测**——需 >100MB 出网，1Mbps 下不值得）| 体型接近上限的书可能被 CF 直接 **413**（到不了应用层，前端只显示 HTTP 状态，无中文提示）|
| 2 | 上传**全量读进内存** | `web/main.py:333` `data = await file.read()` → 100MB 一次性进 RAM | 服务器仅 3.8GB，与 scan 重型解析并行时有 **OOM 风险** |
| 3 | 无上传进度、无断点续传 | 前端单请求 `FormData` | 用户上行抖动 → 整包重来（大书体感差）|
| 4 | 速度上限在用户侧 | 见上表 | 服务端优化空间有限 |

**替代方案对比（若确实要改善上传体验）**：

| 方案 | 内容 | 解决 | 成本 | 风险 |
|---|---|---|---|---|
| **A 流式落盘 + 进度条** | 分块读写 `UploadFile`（不整块进内存）+ XHR `upload.onprogress` | #2 #3 | 低（半天）| 低 |
| **B 上限下调 + 明确报错** | 上限降到 CF 安全线（如 95MB）+ 超限给中文提示 | #1 | **极低（改 1 行 + 前端文案）** | 低（少 5MB 空间）|
| **C 走服务器分片上传** | 前端切片 → 服务端重组（可续传），绕过 CF 单请求上限 | #1 #3 | 中（新端点 + 分片状态 + 清理）| 中 |
| **D 浏览器 → R2 直传** | presigned PUT 直传 R2 + 服务器拉回 | 仅 #1 | 中高 | 中高：与「本地为唯一真相源」冲突，多一份中间态要清 |

> **建议**：S5 原方案**关闭**；要改善体验就按 **B（一行止血）→ A（流式 + 进度）** 走；**C/D 仅在「真的需要 >100MB 的单本书」时再评估**。

### S6「容量/成本看板」—— 结论：**做轻量版，不做全量版**

**现状基线（2026-09-19 实测）**：

| 项 | 实测 | 相对上限 |
|---|---|---|
| 本地磁盘 `/` | 11G / 40G（**28%**）| — |
| translate 工作区 | 413MB | — |
| scan 目录 | 2.5GB | — |
| **R2 对象** | 12 个 / **207.4MB** | 10GB 免费额度的 **2.0%** |
| R2 成本 | **$0**（免费额度内，egress 免费）| 距 Class A/B 操作上限极远 |

- **R2 成本不是风险**：按当前规模（一本书 ~20MB），10GB 额度可用很多年；把这个当「成本看板」是过度设计。
- **真正的风险是本地磁盘**：40GB 里 scan 的视频临时文件会周期性膨胀（它才是吃盘大户）。
- **「预签名请求量」取不到**：`generate_presigned_url` 是**本地计算**、不产生任何 R2 API 调用；真实用量只能接 CF GraphQL Analytics（需新建带 R2 读取权限的 API Token）。可行的替代是**服务端自记签发次数**（近似下载量，非 R2 官方口径）。

| 方案 | 内容 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| **A 全量看板** | 每日快照 + 趋势图 + CF Analytics（R2 操作数/字节数）+ 预签名计数 + 成本折算 | 高（需 CF Token + 新页面）| 数据完整 | 新增外部凭据与依赖；当前无成本压力，收益低 → **不采用（暂）** |
| **B 轻量看板 ✅ 已实现（v5.9）** | 每日一次采样落 JSONL（`work/.storage_history.jsonl`）+ 存储页「容量趋势 · 近 30 天」内联 SVG 双折线 + **阈值并入 S3 守护** + 服务端预签名计数 | 已完成（**零新增 cron / 零新增脚本**：采样塞进 `r2_alert.py` 同进程）| 覆盖真实风险（磁盘增长 + 额度预警）| 低 |
| **C 只加告警 ✅ 已实现（v5.9）** | 磁盘 >85% / R2 >80% 额度 / 采样断更 >36h 并入 `r2_alert.py` | 已完成（1 小时）| 有预警、无趋势 | 低 |

**已实现的形态（用户 2026-09-20 决定）**：**C + 精简 B** —— 监护条件扩到 5 个（`diff` / `unreachable` / `disk` / `quota` / `hist`），多条件合并成一条告警；采样与守护同进程（零新增 cron/脚本）；**趋势口径只统计 trs 自己**（不含 scan）。
**保留的知情项**：①磁盘 >85% 的告警是**机器级**（盘满会连带 trs/scan 全挂），趋势图则只画 trs；②趋势需累积 2–4 周才有信息量；③`presign` 计数为服务端自记（近似下载量），R2 官方口径需 CF GraphQL Analytics Token（暂不做）。
