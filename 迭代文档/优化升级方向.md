# 优化升级方向

已实现的优化（截至 2026-09-16）与待评估方向。主要矛盾：**翻译速度**与**内存/并发约束**。

## 一、翻译速度优化（核心）

### 现状基线
- cron 3min × 3 块 = **60 块/h** → 200 块 ≈ **3.3h**
- 瓶颈：Hermes cron 3 分钟硬中断 + `delegation.max_concurrent_children=3` + 3.8GB 内存

### 方案对比

| 方案 | 配置 | 吞吐 | 200 块耗时 | 风险 | 状态 |
|---|---|---|---|---|---|
| A 现状(cron) | 3min × 3 块 | **26 块/h 实测** | **7h45m 实测**(200块) | 无 | ✅ 已上线 |
| B 每轮 6 块 | 5min × 6 块 | 72 块/h 理论 | 2.8h | **高**：并发上限 3 + 6 子代理 OOM | ❌ 不可行 |
| C 脚本直连 API | 后台脚本 3-4 并发 | 120–400 块/h | **30min–1.5h** | 中：prompt 复制度需 A/B 验证 | ❌ 已被 D 取代 |
| **D 脚本直连(amd)已实施** | systemd 守护 3 并发 | **~110-170 块/h 实测** | **~2h** | **已 A/B 验证通过** | ✅ **2026-09-17 上线** |

### D 方案（脚本直连 API）—— 已实施 ✅

**原理**：绕开 cron agent + delegate_task，写 `translate_direct.py` 由 systemd（translate-direct.service）常驻守护：
```
循环(pick 3 块) → ThreadPool(3) 直调 amd API(prompt=skill 模板+术语表)
   → 写 output → fix_images(补缺失图片引用) → finish → 全书完成 → request-merge → watcher merge
```

**实测结果（2026-09-17，abtest 测试书 37 块）**：
| 指标 | 实测值 |
|---|---|
| 单块耗时 | **47-65s**（reasoning_effort=none）|
| 全书 37 块 | **22 分钟**（~1.7 块/min，≈110 块/h）|
| 内存 | **10.8M 常驻**（systemd MemoryMax=1G）|
| 质量 | 与 cron 版本相当（A/B 对比通过）|
| 成品 | HTML/DOCX/EPUB/PDF 5 格式全生成 |

**关键发现：reasoning_effort 是吞吐杀手**（A/B 测试意外暴露）：
| effort | 单块耗时 | 结果 |
|---|---|---|
| none | 47-65s | ✅ 快且稳 |
| minimal | 180s | ❌ 超时 |
| medium | 141-144s | ⚠️ 慢（1536 reason tokens 白烧）|
| xhigh | >180s | ❌ 超时 |
→ 翻译是直译任务不需要推理，**D 默认 reasoning_effort=none**（2.7x 提速、无超时）

**复用**：consumer.py 队列逻辑、run_state/glossary 接口、merge watcher、progress.json（SSE 无缝可见）
**新增**：`translate_direct.py`（API 客户端+主循环+direct.log）、`fix_images.py`（图片引用修复后处理）

**互斥协调**：D 服务 active 时 cron 只待命（cron prompt 加 systemctl 守卫）；D 失效时 cron 自动接管兜底

**Pitfalls（实测踩坑）**：
1. **finish 的 all_done 不写 merge_request.json** → watcher 不合并。须在 finish 后显式调 `consumer.request_merge(job_id, title)` 才能触发构建。
2. **直连 API 会丢图片引用**：插图密集 chunk（如 chunk0003）模型把整块 `![](images/xxx)` 全丢 → merge image validation 失败卡死。须跑 `fix_images.py` 后处理补回。
3. **默认 provider 已切 amd-radeon**（DeepSeek-V4-Flash），key 从 `AMD_RADEON_API_KEY` 读（不硬编码）。

## 四、通道可用性（2026-09-19 新增，重要）

**现状（2026-09-19 19:50 更新）**：曾出现免费通道**同日双失效**（amd 对话模型全部下线、ark 周配额耗尽 9/21 0点重置）。现已把 **deepseek 官方 flash 作为首位通道**——**网关主通道与 D 引擎 `PROVIDERS` 两边口径一致**，免费通道降为兜底。详见问题记录 #29、版本演进 v5.6。

| 组件 | 通道来源 | 当前状态 |
|---|---|---|
| `translate_direct.py`（D 主引擎）| 自己维护 `PROVIDERS=[deepseek, ark, amd]` | ✅ 首位 **deepseek 官方 flash**（19:50 重启生效，v5.6）|
| Hermes cron（兜底）| 网关主通道（deepseek 官方）| ✅ 可用 |
| 网关本身 | deepseek 官方 + fallback 首位 ark | ✅ 可用 |

**教训**：D 引擎的通道配置**独立于网关**，两边共用同一批 key 却各自维护清单——通道变更必须**两边同时复核**。

## 五、网络带宽（2026-09-19 实测，重要）

评估 E 方案疗效时顺带测出的**真实瓶颈**（脚本：`/root/scripts/net_speed_probe2.sh`、`egress_probe.py`）：

| 方向 | 实测 | 含义 |
|---|---|---|
| VPS 出网（上行） | **~110 KB/s（≈1 Mbps）** | **本项目真正的瓶颈**：R2 全量归档 207MB 要 ~33 分钟；**任何对象存储/图床/同步上传都必须单分片串行**（问题 #31）|
| VPS 入网（下行） | 5.5–8 Mbps | 上传图书、拉取 chunk 够用（与上行**不对称 6–8 倍**）|
| 经 Cloudflare 下载本站成品 | ~109 KB/s（`cf-cache-status: DYNAMIC`）| 53MB PDF ≈ 8 分钟；CF 不回源缓存（内容需鉴权），下行被**回源上行**拖住 |
| R2 预签名直下 | 与 CF 同量级，但**只吃 R2↔浏览器，不占 VPS 出网** | E 方案的收益实际在这里 |

**结论**：手册给 E 方案的理由（省服务器内存 / 省流量）**在本机并不成立**——实测限速拉 53MB 时 translate-web RSS 仅 **65 → 69MB**；开机 5.4 天 TX 累计 6.14GB、14 天下载 47 次，流量远未触顶。**但 E 方案歪打正着**：它精准绕开了 1Mbps 上行这个真瓶颈。

**替代方案 B（升火山引擎出网带宽）—— 已评估、不采用**：比 R2 更直接地解决根因（0 代码改动），但**用户 2026-09-19 决定不升级带宽**（成本考虑）；分发继续由 R2 承担，本项关闭、不再评估。若日后上行成为硬约束再重启讨论。
