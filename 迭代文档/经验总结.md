# 项目经验总结

从单 skill 到完整线上系统的全过程复盘。每条经验对应一个关键决策。

---

## 一、架构设计

### 1. 「skill + Web + cron」三段式是最优解

```
skill（翻译引擎）  ←──  web（查看/上传/任务界面）  ←──  cron（自动驱动）
book/scripts/           web/main.py + static/           ab9ef9653179
```

- **skill**：纯函数流水线（convert → 翻译 → merge），无状态、可脚本化、可测试
- **web**：只做「展示 + 任务编排」，翻译 LLM 工作全部交给外部
- **cron**：3 分钟窗口内做最小的 LLM 工作，机械操作全部脚本化

**核心收益**：任何一个环节可以独立替换。Web 挂了翻译照跑；cron 挂了可以手动补跑；skill 升级不动 web。

### 2. 把「机械操作」和「LLM 工作」彻底分离

这是 P3b 最重要的决策。cron 每 3 分钟被硬中断，所以：

| 工作类型 | 谁做 | 为什么 |
|---|---|---|
| 队列扫描/pick/record/进度/merge 请求 | `consumer.py`（脚本，毫秒级） | 不受 3 分钟窗口影响 |
| 翻译 chunk + 书名 | cron agent（delegate_task） | 必须用 LLM |
| merge 构建（分钟级） | **Web 后台线程**（60s watcher） | merge 太慢，放 cron 必被掐断 |

**教训**：不要把「慢的构建步骤」放进有时限的调度器里。

### 3. 文件系统即数据库

任务队列（`jobs/`）、进度（`progress.json`）、术语表（`glossary.json`）、翻译状态（`run_state.json`）全部用 JSON 文件而非 SQL/Redis：

- 零依赖、崩溃可读、重启无损
- 任何脚本（consumer.py）都能直接读写，不需要连库
- 3.8GB 内存服务器上没有多余服务可跑

**代价**：并发写需要小心（用原子写：write temp + rename）。

### 4. 幂等是断点续译的前提

**所有步骤都设计为可重入**：
- pick 检测 output 已存在 → record_only（不重译）
- merge 检测 run_state 全部 done → 才允许 merge
- 术语表变化 → affected_chunks 精确重置，不动已译块

**规则**：一个 chunk 的 output 文件 = 唯一的「已翻译」事实来源，run_state 只记录不决策。

## 二、调度与并发

### 5. 3 分钟窗口下的吞吐设计

Hermes cron 硬中断 3 分钟 → 每轮有效翻译时间 ≈ 150s（扣掉启动/加载/队列开销）。

**参数推导**：
- 并发上限：`delegation.max_concurrent_children = 3`（配置硬限制）
- 每轮 3 块并行 × 单块 ~90s → 每轮约 3 块
- cron 间隔：必须 ≥ 窗口（3min），否则 run 重叠并发翻倍 → 内存爆
- 最终：3min × 3 块 = **60 块/h**（5min 时 36 块/h）

### 6. 并行不是越多越好（这台机器）

服务器 3.8GB RAM + 2GB swap，scan 常驻 ~1GB：
- 每个 delegate_task 子代理 = 一个 agent 运行时进程
- **6 并发必 OOM**（安全线 3.05GB，峰值已见 2.96GB）
- 3 并发是内存安全上限，且是 config 并发上限

### 7. 更快路径 = 绕开 agent 层（D 方案，已实施）

脚本直连 LLM API（`translate_direct.py`，systemd 守护 `translate-direct.service`，2026-09-17 上线）：
- 无 3 分钟窗口、无 agent 启动开销、并发自控（ThreadPool 3）
- 内存 **10.8M 常驻**（vs agent 方案 ~1GB），速度 **~110 块/h**（vs cron 26 块/h 实测）
- **A/B 实测通过**：译文质量与 cron 相当，5 格式成品全生成

**核心经验：reasoning_effort 是吞吐杀手（A/B 测试意外发现）**
- 翻译是直译任务**不需要推理**：amd 通道 `reasoning_effort=medium` 让 3KB 小 chunk 花 141-144s（白烧 1536 reasoning tokens），minimal 直接 180s 超时
- **`none` 只要 47-65s 且质量等同**（连章节标题都比 cron 翻得更准）→ D 默认 `reasoning_effort=none`
- 教训：**别让直译任务做深度推理**，thinking effort 对翻译是纯负收益

**两个必踩坑**（详见《问题记录》#17 #18）：
- ① `consumer.finish()` 全 done 不写 merge_request.json → 须显式 `request_merge` 触发
- ② 直连 API 在插图密集块丢整块图片引用 → `fix_images.py` 后处理补回（prompt 约束对直连不可靠）

详见《优化升级方向.md》。

## 三、LLM 与翻译质量

### 8. 术语表「保存即重译」闭环

PUT 术语表 → run_state 算 affected_chunks（内容哈希变化）→ 已完成书重置 ready → cron 自动接手。

**实测**：Alice 术语注入后，重译 chunk 含「爱丽丝」「白兔先生」——术语表真实影响翻译，不是摆设。

### 9. 翻译质量的三个关键约束（skill 蓝图里）

1. **图片引用保留**：`![图 N](images/xxx.png)` 必须原样保留，否则 merge 后图片丢失
2. **格式约束**：标题层级/代码块/列表结构不破坏（merge 依赖）
3. **术语表注入**：prompt 里给死术语对照，专有名词不瞎译

### 10. 空 chunk 是合法产物

convert 对 PDF 末尾空白页会生成 0 字节 chunk——**这是正常的**。merge 校验必须容忍 source_empty，否则整书被一个空块卡死（BDS 教训）。

## 四、部署与运维

### 11. Caddy + Cloudflare 反代链路

```
浏览器 → Cloudflare(HTTPS) → Origin Rule(Hostname→8080) → Caddy(按 Host 分流) → 8788/8787
```

- **Origin Rule 必须用 Hostname 字段**（URI 字段匹配 URL 路径，永不匹配域名）
- Caddy 按 Host 头分流多站，端口固定 8080（CF 无法猜端口）
- **鉴权在应用层**（2026-09-16 起）：Caddy 只做反代、**不再 basicauth**——Caddy 能回答「你是谁」（HTTP 认证），回答不了「你能干什么」（读/写/下载分级）。需要「游客只读 + 管理员全功能」这种档位时，认证必须下沉到 FastAPI 中间件，详见 #19

### 12. systemd 管理 + 崩溃自愈

`translate-web.service`：Restart=always + 开机自启。网关重启用 `systemd-run --user` 延迟定时器（直接 systemctl restart 会杀自己会话）。

### 13. 审批模式纪律

服务器操作习惯：**临时关审批 → 执行 → 立即恢复 manual**。长命令/管道/rm 会触发审批，内联 python 会挂起，pkill -f 会自误杀——这些都是踩过的坑，见《问题记录》。

## 五、前端

### 14. 骨架与 JS 必须同步交付

**最大前端事故**：index.html 有完整 UI 骨架（全选/上传/回收站/折叠），app.js 却缺对应函数——上线即死的按钮，直到 9/16 功能迭代才补全。

**教训**：每次加 HTML 骨架，必须同时加 JS 函数，并用 `grep 函数名` 双向核对。

### 15. 视觉一致性 = 设计令牌

CSS 变量（`--paper`/`--ink`/`--accent`/`--line`）+ 深色自适应 + font-mono 小标签 + SEC 分区 = scan/博客一致的档案感。新功能直接复用令牌，不引入新色值。

### 16. SSE 做实时 + 轮询兜底

SSE 提供秒级体验（终态立即推），15s 轮询兜底（SSE 断线自动恢复）。双保险不冲突。

### 17. 进度条：后端给结构化数据，前端保留兜底解析

后端 `books.py` 把状态串解析成 `{done,total,pct,active}`（`progress` 字段），前端 `progOf()` **同时保留自己解析状态串的兜底**。收益：静态文件更新即生效，**后端没重启/接口没更新时进度条照样工作**——部署顺序不再是硬约束。

**自动刷新要分级**：书库页可以整表重绘（4s），详情页**只刷头部进度**（否则会把用户正在看的译文/对照面板冲掉）。且只在有 `active` 书时开定时器，全部完成后 `stopProgPoll()` 自动停，不空转。

### 18. 服务端生成 PDF：必须用像素级判据验证

`pdftotext` 能提取中文 / `pdffonts` 有字体名，都**不能证明**字形真的画出来了。唯一可靠判据是**渲染成图后看墨迹**：取中文词 bbox → 裁切 → 算暗像素占比（正常 6%–10%，空白 0%）。工具：`/root/scripts/pdf_zh_check.py`。

配套环境：`fonts-noto-cjk` 是**必需依赖**（Debian 最小安装默认没有）；装完记得 `fc-cache -f`。同类盲区：服务器上一切「本机浏览器看得见、服务端生成却不对」的产物（PDF/缩略图/截图）。

## 六、鉴权与前端工程

### 19. 认证在反代层，授权在应用层

**决策**：站点从「Caddy basicauth 一把锁」改成「应用层 `AuthMiddleware` + 游客只读白名单」。

**为什么**：basicauth 是**二值认证**，没有「只读参观」这一档；且 401 由 Caddy 直接返回，前端拿不到可编程响应——自定义登录框、403 引导、按接口分级统统做不了。**反代层能回答「你是谁」，回答不了「你能干什么」。**

分层结果：

| 请求 | 判定 | 响应 |
|---|---|---|
| 无 `Authorization` | 游客 | 白名单只读放行；写操作 **403 + `X-Guest-Only: 1`** |
| 有头 + bcrypt 校验通过 | 管理员 | 全功能 |
| **有头但校验失败** | — | **401，不降级为游客**（否则「伪装成游客」即可绕开白名单与限频）|

敏感资源（任务详情/SSE、回收站、`/download/`、json/yml 等内部文件）对游客一律拒绝；游客搜索按 IP 限频 10 次/分。

**收益**：站点可以对外「参观」，管理功能严格受保护；权限规则集中在 `guest_rules.py`，改规则不用碰反代配置。

### 20. 凭据存 localStorage = 只有显式 fetch 带得上

前端把 Basic 凭据存 `localStorage`，再**手动**加到每个请求头上——这意味着「让浏览器自己发请求」的写法一律不携带认证：

| 写法 | 是否带认证头 |
|---|---|
| `fetch(url, {headers:{Authorization}})` | ✅ |
| `window.location.href = url` | ❌ |
| `<a href>` / `<img src>` / 表单提交 | ❌ |

所以需要鉴权的下载/导出必须走 **`fetch` → `blob` → `URL.createObjectURL` → `<a download>`**（顺带保留文件名、顺带能拦截 401/403 弹登录框）。**换个写法就可能全线 403，这不是后端问题。**

### 21. 改公共工具函数前先 grep 全部调用点

`has(obj, key)` 这类工具函数的**参数语义是隐式契约**（要不要带 `book.` 前缀？）。新增调用方按另一种口径传参 → 全线静默失效（提示「文件不存在」），而且报错位置离根因很远。

**纪律**：改工具函数 → `grep -n 函数名 web/static/*.js` 逐个核对调用点；改完自测**所有**调用点（预览/原文/译文/下载），不只测新改的那个。

### 22. 静态资源必须带版本号

`<script src="/static/app.js?v=20260919a">`——纯静态前端没有构建哈希，浏览器缓存会造成「代码已改、服务已重启」的错觉（实际还在跑旧 JS）。**每次改前端就递增版本号**，这是零成本的排查省时手段。

## 七、分发与存储

### 23. 大文件下载不要经过浏览器内存（兼论流量外移的边界）

原下载实现是 `fetch + Blob`：**整个 PDF 先进 JS 内存再落盘**——53MB 的书在低配机器/手机上就是卡顿甚至崩标签页。E 方案（R2）把成品分发挪出 VPS：后端只签发**预签名 URL**，前端用 `window.location.href` 做**顶级导航**，浏览器直接把响应写磁盘，VPS 也不出流量。

三个可复用的判断：

- **顶级导航 ≠ fetch**：导航不受 CORS 约束、不占 JS 内存，适合「一次性下载」；代价是拿不到响应体、不能加自定义头——所以**鉴权必须发生在签发 URL 那一步**（`/api/download/` 端点需管理员凭据），预签名 URL 本身是「限时通行证」（15 分钟）。
- **对象存储是分发通道，不是备份**：本地成品文件必须保留——状态判定（`_status()` 判 `done`）与文件清单（`_file_summary()`）都依赖本地存在与大小。删本地 = 书状态倒退（问题记录「硬约束 1」）。
- **失败要静默降级**：`r2.py` 全部失败路径只记日志、返回 `None/False`，端点退回本地直连。**存储是可选的加速器，不能变成单点。**

**设计期就该避开的一个坑**：新端点路径必须落在显式白名单**之外**。`guest_rules.guest_read_allowed` 是「逐条前缀匹配 + 末尾 `return False`」的白名单，端点放 `/api/download/` 天然被拒；但若图省事放 `/api/books/{name}/link/...`，会命中 `startswith("/api/books")` 分支，而 `_GUEST_DENY_SUB` 只匹配 `/download/` → **游客直接白拿预签名 URL**。加端点时先读一遍白名单再定路径，并**实测一次不带凭据的返回码**。

## 八、安全

### 24. 凭据/密钥/哈希永不进仓库——它们是配置，不是代码

**失误**：访客模式改造时把管理员 bcrypt 哈希内联在 `main.py` 里并推到了公开仓库（scan 同）。当时的心理是「bcrypt 不可逆，应该没事」——**错在两点**：① 代价因子 14 的哈希可离线爆破，密码强度不够就等着被撞；② **哈希泄漏无法撤回**（git 历史公开、可能有 fork），唯一补救是**轮换密码**——而轮换会让所有已保存的客户端凭据失效，代价远高于当初老实写到文件里。

**做法**：

- 密钥材料（API key、密码、**密码哈希**）一律放服务器本地文件（`/root/.xxx-cred`、`chmod 600`、**仓库目录之外**），代码只读文件
- 读取器必须 **fail closed**：读不到就拒绝管理员登录（游客浏览照常），**绝不回退到硬编码默认值**
- 轮换脚本化：`/root/scripts/rotate_admin_cred.py`（生成新密码 + bcrypt 哈希 → 写凭据文件 → 重启生效），配套 `/root/scripts/verify_auth.py`（新密码 / 旧密码 / 游客 三类回归）
- 上线前做泄漏审计：内容级 `grep -rnE '\$2[aby]\$|sk-|AKIA' --include=*.py`，再加 `git log -p` 查历史
- 一旦哈希进过公开仓库：**立即轮换**，别指望「删掉就没事」

### 25. 1Mbps 链路上，默认并发的对象存储上传必然失败

首次全量同步 R2 时 12 个文件只失败 2 个——恰好是最大的两个（53.5MB / 42.5MB）。原因不在 R2，而在 **boto3 `upload_file` 默认 `max_concurrency=10`**：10 个分片抢 110KB/s，每片仅 ~10KB/s，8MB 分片要 800s，远超 `read_timeout` → 连接被服务端切断。小文件走单请求，所以全过。

**可复用的判断**：

- **受限带宽上，先问「默认并发是多少」**：云 SDK / aws-cli / 镜像工具默认并发都是按"带宽充足"假设定的（boto3 = 10）。1Mbps 上并行只会让每条连接都慢到超时，等于全部失败。
- 症状很好认：**大文件必失败、小文件全成功**，且报错是 "Connection was closed before we received a valid response"。
- 修复是双向的：**并发降到 1**（`max_concurrency=1, use_threads=False`）**+ 超时放大到实测所需**（8MB/110KB/s ≈ 78s → `read_timeout=600`）。
- 幂等设计救了这次事故：`upload()` 用 `head_object` 比对尺寸跳过已传文件，重跑只补失败的 2 个，不用从头再来。
- **跨系统断言只能真拉一次远端，不能靠「预演」**：`r2_sync.py --dry-run` 只枚举本地待传文件、**压根不查远端**，却打印「成功/已存在 12，失败 0」——差点据此宣布归档完成，实际桶里只有 11 个（问题 #32）。**dry-run 的语义必须读代码确认**；「本地说一切正常」与「远端确实一致」是两件事，归档/备份/投递这类断言要用真实列举（`list_objects_v2`）对账：`/root/scripts/r2_reconcile.py`。

## 九、通道与依赖

### 26. 通道清单分散在多处——变更要一起改，新链要先探「能力」再探「连通」

同一批 API key 被**三个地方各自维护**：Hermes 网关的 `config.yaml`（主通道 + fallback）、`translate_direct.py` 的 `PROVIDERS`、各式探测/运维脚本。实测后果：免费通道同日失效后网关切 deepseek 官方**恢复了**，但 D 引擎还卡在 `[amd, ark]` 两跳全废——**「网关好了、引擎还哑着」**这种错位不会自己暴露，因为两边各自「看起来都正常」。

四条可复用做法：

- **改通道前先列出全部使用者**：`grep -rn "chat/completions" --include=*.py` 加网关 `config.yaml` 的 `providers:`；改完**每一处都实测一次**（本轮：网关日志 + 引擎 `api_translate()` 真实 chunk 调用）。
- **接新链先探「能力」，不只探「通不通」**：新链是否接受既有参数（本项目是 `reasoning_effort=none`——翻译任务不推理的既有策略）、模型名是否在线、限流口径。探测脚本化（`probe_deepseek_effort.py` 一轮跑三种取值、10 秒出结论）比在业务代码里撞 400 便宜得多。
- **顺序即成本**：`PROVIDERS` 首位就是默认付费对象。免费在前、付费兜底是省钱策略；用户要求「默认官方」时则相反——**顺序决策必须写进文档**（README + 问题记录 + 版本演进三处都写），别只留在代码里，否则下次省费/恢复免费通道时没人知道该动哪。
- **重启前先看队列**：D 引擎重启即开始消费队列（`no_ready_task` 才是安全的重启时机）——否则一次「无害重载」会直接开跑一本付费大书。

## 十、存储页与下载源治理（S2/S3/S4）

### 27. 守护/告警脚本 = 一台状态机，必须按状态机测（不是「跑一次看有没有报错」）

归档守护 `r2_alert.py` 只有一句话的业务目标（「差异持续就提醒」），但真正决定它好不好用的是**状态机**：首次发现要不要立刻叫？瞬时抖动怎么办？同一个问题会不会每半小时刷一次屏？修好了要不要告诉人一声？脚本自己崩了算谁的？本轮把它落成 5 个显式状态 + 2 个开关（`--selftest` 注入条件、`--age` 假装已持续），**9 个状态逐条实测**：

| 状态 | 期望 | 实测 |
|---|---|---|
| 差异 <30min（观察期）| 静默 | ✅ 0 字节 |
| 差异 >30min | 告警一次 | ✅ 带明细与处理建议 |
| 同问题再跑 | 静默（6h 去重）| ✅ 0 字节 |
| 恢复正常 | 发一条「已恢复」| ✅ 43 字节 |
| 恢复后再跑 | 静默 | ✅ 0 字节 |
| 真实巡检（无差异）| 静默 | ✅ 0 字节 |
| 凭证被移除 | 静默降级（功能未启用≠故障）| ✅ 0 字节 |
| 脚本自身崩溃 | 告警（不能静默失效）| ✅ 含异常摘要 |
| 崩溃后重复 | 静默（同样去重）| ✅ 0 字节 |

四条可复用结论：

- **「静默正常」是告警脚本的核心指标，不是副产品**：搭配 `no_agent` cron（stdout 原样投递）时，**零输出 = 用户零打扰**。所以每一态都要用「字节数」断言，而不是「看着没报错」。
- **必须区分「未配置」与「故障」**：R2 凭证没填（功能未启用）和 R2 连不上（真故障）在代码里只差一个分支，对用户却是「别烦我」和「快来看」的区别。
- **告警要有去抖 + 去重两道闸**：只做「差异>0 就报」会在同步窗口期刷屏；只做去重又会在首次就误报。**先在观察期静默攒够 30 分钟，再查 6 小时重提窗口**。
- **「恢复通知」比告警更值得发**：告警的读者会自己去处理，但**没人会去确认它好了没有**——一条「已恢复」把闭环补上，成本一条消息。

### 28. 破坏性运维操作：删前复核、只删副本、把不安全的部分交给人

存储页要给「一键清理孤儿对象」（R2 上有、本地已不该有的对象）。这类按钮最容易变成事故源，落地的安全设计是四条：

- **后端不复用前端的判定结果**：POST 的 key 到了后端**重新拉一次远端**核实它现在仍是孤儿——用户可能在页面停留的几十秒里刚好补传了文件（TOCTOU）。
- **「本地存在同名成品」一律拒绝删除**：孤儿判定优先看本地，只要 `local_map[book][rel]` 存在就 refuse，并把原因回给前端。**宁可少删，不可错删**——远端副本删了还能重传，本地唯一真相源删了就没了。
- **只动远端副本、绝不动本地文件**：GC 函数里没有任何本地删除路径（连回收站都不碰），语义边界写在 docstring 里。
- **读不到远端就整体放弃**：`objects_all() is None` 时直接返回错误（`不冒删错的风险`），不会退化成「按前端给的列表盲删」。

实测三条拒绝路径 + 一条真删路径：本地存在的 key → refuse；`/etc/passwd`、`hack/x/y` 等非法路径 → refuse；**真造一个孤儿对象**（`books/__gctest__/book.pdf`）→ 被识别为 `ghost_book` → 删除成功 → `objects_all()` 复核已清空；最后确认被拒绝的那本书**本地下载仍 200**。

**可复用的判断**：破坏性操作的安全不来自「前端确认框」，而来自**后端每次都重新独立判定一遍**——前端 confirm 只防误触，不防过期视图与恶意请求。

### 29. 新增管理员端点的安全默认值：靠 `fail-closed` 白名单，而不是靠记得加鉴权

S2/S4 新增了 4 个端点（`GET/POST /api/storage*`、`GET/POST /api/settings`），**没有为它们写一行鉴权代码**，却是管理员专享——因为 `guest_rules.guest_read_allowed()` 是「显式白名单 + 末尾 `return False`」：游客只能读白名单里的读端点，**任何新端点默认落在「需管理员」一侧**。实测：游客 `GET /api/storage` → **403**、`GET /api/settings` → **403**、`POST /api/settings` → **403**（`method in (GET/HEAD/OPTIONS)` 之外的写操作本就不进游客分支）。

这正是「默认拒绝」优于「默认允许」的实操价值：安全不需要每加一个端点都重新想一遍，**只在「要放开给游客」时才需要显式动白名单**（放开是少数、需要 conscious decision 的动作）。反例是 v5.7 的知情项——`/api/books` 是游客白名单内的读端点，所以挂在它上面的存储汇总**顺带对游客可见**；本轮 S2 把完整存储页做成独立管理员端点，正好收口了这个边界：**汇总仍在书卡上（游客可见），逐书对账与清理只在存储页（管理员）**。

**注意**：这条只对「路径前缀型」白名单成立。如果哪天把新端点做进 `/api/books/...` 这类已在白名单内的前缀下，就会**默认放开**——那时必须显式加进 `_GUEST_DENY_SUB`（v5.7 的 `/api/download/` 就是刻意避开 `/api/books` 前缀的，注释里写了「不要改这个路径」）。
